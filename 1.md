# Per-Folder Image Attachment Management

## Purpose and Scope

Implement image attachment management in the existing Patchwork project at `D:\ideaProjects\obsidian-patchwork`. The current target vault is `D:\my-notes`; implementation must use the active vault rather than hardcode this path.

The required outcome is:

- Each note directory stores images in its own `assets` subfolder.
- These attachment folders can be hidden from the Obsidian file explorer without affecting image rendering or indexing.
- Users can manually find, review, and trash images that are no longer referenced anywhere in the vault.

This document is an implementation handoff. Creating this document does not authorize changing the vault, installing plugins, building the project, or deploying changes.

## Implementation Ownership

| Capability | Implementation |
| --- | --- |
| Save new attachments beside their notes | Reuse Obsidian's native attachment location setting. |
| Hide attachment folders | Implement within the existing Patchwork plugin and style system. |
| Scan for unreferenced images | Develop within an existing appropriate Patchwork plugin. Reuse Obsidian APIs where suitable. |
| Preview, select, and trash images | Develop within that same plugin. |

Do not install or depend on a third-party attachment cleanup plugin. Existing community plugins are references only. Inspect the repository before choosing the owning plugin; do not create another standalone plugin unnecessarily.

## 1. Attachment Storage

Use an ordinary directory named `assets`, not `.assets`. Dot-prefixed directories are ignored by Obsidian and are unsuitable for this native attachment workflow.

Example:

```text
Technologies/
├── Java/
│   ├── Collections.md
│   ├── Streams.md
│   └── assets/
│       └── collections.png
└── Redis/
    ├── Cache.md
    └── assets/
        └── cache.png
```

Requirements:

- Configure the native attachment location to a specified subfolder under the current note's folder, with the subfolder name `assets`.
- Notes in the same folder share one `assets` directory; notes in different folders use separate directories.
- Newly pasted images and images imported by drag-and-drop use this location. Do not reinterpret a link to an existing vault image as a request to move that image.
- Create the directory on demand through the native attachment workflow; do not precreate empty folders throughout the vault.
- Notes at the vault root use the root-level `assets` folder.
- Preserve native filename conflict handling; never overwrite an existing image because its name matches a new attachment.
- Support ordinary relative references such as `![Collections](assets/collections.png)` without forcing conversion of existing Wiki links.
- Reuse native settings instead of adding custom clipboard or drag-and-drop handling unnecessarily.
- Explain that the native attachment location can apply to other newly imported attachment types as well. Cleanup in this feature remains limited to images.

## 2. Hide Attachment Folders

Requirements:

- Provide a persistent setting to hide or show attachment folders in the Obsidian file explorer.
- When enabled, hide folders whose complete name is exactly `assets`, at every directory depth.
- Do not hide folders such as `my-assets` or `assets-backup`.
- Apply presentation changes only. Do not rename folders, set filesystem hidden attributes, or exclude attachments from indexing.
- Image rendering, reference resolution, and cleanup scanning must continue to work while folders are hidden.
- Turning the setting off, or disabling the owning plugin, must restore normal explorer visibility.
- Follow the project's existing settings, styling, and lifecycle conventions.

## 3. Find Unreferenced Images

Provide a manually invoked command or existing-menu action for scanning unreferenced images.

### Candidate Files

- Limit cleanup candidates to supported local image files located within `assets` directory trees.
- Define supported image extensions explicitly using Obsidian's supported formats where appropriate.
- Exclude configuration, version-control, trash, and known backup directories from cleanup targets.
- Never include Markdown documents, non-image attachments, or remote image URLs as deletion candidates.

### Reference Detection

- Check references across the entire active vault, not only the directory containing a candidate image.
- Resolve references to actual vault file paths. Filename matching alone is insufficient.
- Handle identical filenames in different folders, relative paths, Chinese characters, spaces, and URL-encoded paths.
- Recognize Markdown image embeds, Markdown reference-style links, Wiki embeds, and ordinary links targeting images.
- Account for Canvas file references and Excalidraw image references. Inspect their actual storage formats before claiming support.
- Reuse Obsidian's resolved-link metadata and file-resolution APIs where reliable. Supplement them only where necessary.
- Wait for reference metadata to be ready before producing actionable results.
- Treat unsupported or ambiguous references as uncertainty. Do not silently classify affected images as safe to delete.
- If a format cannot be reliably checked and the affected images cannot be determined, report the limitation and disable cleanup for that scan rather than present an incomplete scan as conclusive.
- Excluding a directory from cleanup targets must not automatically exclude legitimate references originating there. Document how trash and historical backups are treated separately from active vault content.

An image with no detected references is a review candidate, not proof that the user no longer needs it. Newly imported images may not yet have been inserted into a note.

## 4. Review and Cleanup

### Results Interface

Show:

- A thumbnail or an accessible image preview.
- Filename and path relative to the vault root.
- File size.
- Grouping by directory.
- Total candidate count and size.
- Selected count and size.
- Detection limitations or uncertainty that affect cleanup eligibility.

Support individual and bulk selection. Select nothing by default. Keep the interface responsive with large attachment collections; load previews on demand and release temporary resources when the view closes.

### Cleanup Behavior

- Only process files explicitly selected by the user.
- Show the selected count and size before confirming cleanup.
- Revalidate references immediately before moving each selected image to trash, including changes made after the scan.
- Skip files that gained a reference, moved, disappeared, or cannot be confidently evaluated. Report the reason.
- Use Obsidian-supported recoverable trash handling. Do not permanently delete files, even if the vault's general deletion preference is permanent deletion.
- If recoverable trash is unavailable or fails, report the failure. Do not fall back to permanent deletion.
- Report successful, skipped, and failed operations and explain where trashed files can be recovered.
- Prevent overlapping cleanup operations and update stale scan results appropriately.
- Do not delete empty directories as a side effect.

## 5. Explicit Exclusions

- No third-party cleanup plugin installation or runtime dependency.
- No automatic image deletion when a note is deleted.
- No default background or scheduled cleanup.
- No automatic cleanup immediately after pasting an image.
- No permanent deletion workflow in this scope.
- No migration of historical images or bulk rewriting of existing Markdown references.
- No automatic relocation of existing images when notes move.
- No changes to unrelated code-block themes, syntax highlighting, run-code controls, or other project features.

Historical image migration, if requested later, requires a separate plan that updates all affected references.

## 7. Acceptance Criteria

| Scenario | Expected outcome |
| --- | --- |
| Paste images into notes in different folders | Each image is saved in the corresponding folder's `assets`. |
| Paste images into two notes in the same folder | Both use the same local `assets` directory. |
| Paste an image into a root-level note | The image is saved in the root-level `assets`. |
| Import an image with an existing filename | Existing image contents are preserved. |
| Hide attachment folders | All exact-name `assets` folders disappear from the explorer; embedded images still render. |
| Show attachment folders or disable the plugin | Normal explorer visibility is restored. |
| Use a folder named `assets-backup` | It is not hidden by the exact-name rule. |
| Two notes reference the same image; one note is deleted | The image remains classified as referenced. |
| A note in another directory references an image | The image is not a cleanup candidate. |
| Two directories contain images with identical names | References are evaluated independently by resolved path. |
| A supported Markdown, Wiki, Canvas, or Excalidraw reference uses an image | The image is protected from cleanup. |
| A relevant reference cannot be reliably resolved | The limitation is visible and affected cleanup is blocked. |
| An image gains a reference after scanning | Cleanup skips it after revalidation. |
| An unused image is selected and cleanup confirmed | It moves to recoverable trash. |
| Trash handling fails or permanent deletion is configured | The image is not permanently deleted. |
| An image is not selected, is outside eligible directories, or is a non-image file | It remains unchanged. |

These criteria describe expected behavior; they do not authorize creating or modifying test code.
